コードレビューは次の8つの観点で見ています。

**セキュリティ** — 悪用できる穴がないか。攻撃者が外から渡した入力が、危ない場所（コマンド実行・SQL・任意ファイル読み・認証バイパス・URL を勝手に叩く等）まで届くかを追跡します。

**速度** — 遅くなる作り方をしていないか。ループの中で DB を叩いていないか、メモリが無制限に伸びないか、よく呼ばれる場所で重い処理が止まっていないか。

**運用** — 本番で壊れた時に原因がわかるか。タイムアウト・リトライの設計、ログとメトリクスが十分か、デプロイで戻せるか、深夜3時に気づける作りか。

**テスト** — 壊れたときにテストが気づくか。新しいロジックや境界値、例外、並行処理のテスト漏れ、テスト自体が脆くなっていないか。

**API契約** — 既存のクライアントを壊していないか。フィールド削除・型変更・HTTP ステータスや認可スコープの変更・DB マイグレーションの非互換。スキーマや migration、SDK を触ったときだけ自動で起動します。

**依存ライブラリ** — 怪しいパッケージを入れていないか。タイポを利用した偽パッケージ、未署名、ライセンス不整合、インストール時に勝手に走るスクリプトなど。package.json などを触ったときだけ自動で起動します。

**設計** — 構造として無理がないか。レイヤ違反、結合が強すぎる、責務が散らばっている、循環依存。「設計も見て」と指定したときだけ起動します。

**読みやすさ** — 半年後の自分が読めるか。複雑すぎる関数、マジックナンバー、コメントの過不足、変更しにくい書き方。「読みやすさも見て」と指定したときだけ起動します。

最後にコーディネーターが全部の指摘を統合して、**マージOK / 要議論 / 要修正** を判定します。重大な問題が1件でもあれば、先頭に🚨を付けて知らせます。

各観点とも「机上の可能性」ではなく「実際にたどり着ける失敗経路」だけを報告する方針です。命名や好みの押し付けはしません。
